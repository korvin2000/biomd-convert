# biomd-convert — project constitution

This file holds the rules that apply in **every** session in this repository. They are binding.

Task-specific briefs are separate documents:

| what | where |
|---|---|
| current refinement campaign brief | `analyze/REFINE-CONVERTER.prompt.md` |
| durable measured state, what remains, what is unreachable | `biomd-convert/CONVERTER-PROGRESS.md` |
| precise open-defect state (generated by L2, below) | `analyze/defects.json` |

A session that has lost its context re-orients from those three plus this file, and from `TaskList`.

---

## 1. What this is

`biomd-convert` is a deterministic-first compiler from legacy HTML to BioMD Lite 1.6. The corpus is ~1000
Russian-language biographies of guitarists and composers, authored in 1998-era Microsoft FrontPage: bloated,
frequently malformed, table-based layout, presentational markup, no semantics. Thirteen pages have
hand-made reference conversions in `biomd-convert/fixtures/`.

Those thirteen are **evidence, not the target**. The product is a rule system that generalizes to the other
~987 pages and to any structurally similar corpus, plus an evaluation apparatus that localizes defects
precisely enough to act on. Both halves are deliverables.

Fidelity means three things at once: conformance to `Biography-Markup.md` under the target profile;
structural and visual equivalence to the references — layout intent, not pixels; and no loss or invention of
content. Moving one while breaking another is a regression.

Environment: Windows, Node ≥ 22, TypeScript/ESM, vitest, parse5, optional Playwright (Chromium measurement),
zod, commander. PowerShell and Bash are both available.

```bash
cd biomd-convert && npm run build && npm test          # build + 239 unit tests
```
```bash
cd biomd-convert && sh bench/run.sh                    # the only trustworthy scalar measurement loop
```
```bash
cd biomd-convert && npm run biomd -- inspect fixtures/html/segovia.htm   # run from source, no build
```
```bash
cd biomd-convert && node dist/cli/index.js diff -c bench/biomd.config.json --json ../analyze/defects.json
```

## 2. Ground truth, highest precedence first

1. **`Biography-Markup.md`** — normative BioMD Lite 1.6 syntax, and §16.3 (no invented content).
2. **`biomd-convert/fixtures/html/*.htm` ↔ `fixtures/out/*.bio.md`** — 13 hand-made pairs. Normative for
   every judgement the spec leaves open. Read them as evidence of intent.
3. **`analyze/analyze.md`** (Russian, per-page complaints) + **`analyze/design.png`** (green frames =
   convert, red = chrome to drop) + `analyze/snapshot_*.png`. The highest-value diagnostic input available
   and the only record of *human* quality judgement; several entries name the exact defect and its cause.
4. **`html-to-biomd_guide.md`, `html-to-biomd_ext_guide.md`** — the manual procedure behind the references.
   Advisory and possibly stale: where a guide contradicts `fixtures/out/`, the reference wins — and say so.
5. **`biomd-convert/CONVERTER-PROGRESS.md`** — current measured state; §5 is what remains. Verify, don't trust.
6. **`CONVERTER-ASSESSMENT.md`, `htm-to-md_utility_plan.md`, `how_to_fix_table_parsing_and_reconstruction.md`**
   — historical. PROGRESS §3 records where the assessment was measurably wrong; that pattern repeats.

## 3. Invariants

The only hard limits. Everything not forbidden here is available, including large architectural change.

1. **Reference integrity.** Never edit `fixtures/html/`, `fixtures/out/`, or `analyze/*.md` / `analyze/*.png`.
   Evidence.
2. **Metric integrity.** Never tune `src/eval/score.ts`, or any instrument built here, to move a number.
   Instruments change only to become *more truthful*, in isolated declared steps, with both sides re-baselined.
3. **No instrument may become the objective.** Scalar score, structural diff, visual diff, LLM judge — each
   is a defect detector, never a thing to maximize. On catching yourself optimizing an instrument's output
   rather than the conversion: stop and say so.
4. **No invented content** (§16.3). Where a reference contains text absent from the source, record it as an
   unreachable ceiling. Never close a gap by fabricating.
5. **No literals law.** No corpus-specific string, class, id, filename or title inside a detector. Lexical
   knowledge (bullet glyphs, label vocabularies, border palettes) lives in documented, language-tagged data
   files, and every rule consulting one degrades gracefully — not breaks — when the list does not match.
   A detector must never be able to name a document.
6. **Determinism.** Same input + `--replay` ⇒ byte-identical output. Diagnostic tools are deterministic too,
   or they are labelled non-deterministic and never gate a decision alone.
7. **Honest measurement.** Report no number not measured, no completion not verified. A crashed conversion
   invalidates that run's measurements — say so rather than reporting the remainder.

## 4. Evaluation is a ladder, not a number

### 4.1 Why the scalar score is not the instrument

`src/eval/score.ts` averages seven multiset F1 axes. That was the right tool while whole tables were
vanishing. It cannot tell you *what* to fix, and its blind spots are exactly where late-stage defects live.
Verified from the code:

- `eval/facts.ts:36` — `directives: Map<string, number>`, name → count. **Every directive property is
  invisible**: an `::: image` with the wrong `size`, `align`, `caption` or `link` scores identically to a
  correct one.
- `links` and `images` fold through `foldTarget` — **a correct target with a wrong label scores perfect**.
- `TableFacts` carries `cols`, `rows`, `header[]`, `cells[]` as flat multisets — **which cell sits in which
  row and column is invisible**, as is per-column alignment.
- text is a word-3-gram multiset over `normalizeForCompare` (`convert-core/conservation.ts:102`), which
  lowercases, strips soft hyphens and folds intra-word hyphens — so **block order, blank-line structure,
  hard breaks, emphasis, case and typography are invisible**, and de-hyphenation quality is invisible by
  construction.
- headings carry level (`facts.ts:132`, `level\tlabel`) but as a multiset — **position, order and nesting
  are invisible**.
- nothing measures containment (an image inside vs outside a `::: column`), `---` separators, list nesting,
  or block ordering.

### 4.2 The levels

A level is only meaningful when the one above it is clean.

**L0 — Gate.** `npm run typecheck`; `npm test`; the mutation suite (§6); zero FAILED conversions in
`corpus run`; `biomd validate` errors not increased; `biomd-ast/read()` warnings on produced output = 0;
conservation ledger clean. Red L0 invalidates everything below.

**L1 — Scalar tripwire.** `sh bench/run.sh`. Deliberately demoted: a *silent-regression detector for areas
not currently under examination*, never a target and never evidence of quality. Given §4.1, an unchanged
score is not evidence that nothing changed. Reference baseline, LLM off, `spec-1.6`,
`layoutFidelity: faithful`, Chromium measurement on: **87.61 % weighted · 239 tests · 14 validation errors
(12 = empty table headers) · 0 structural errors**. A differing number is reconciled before any rule is touched.

Reproduced 2026-08-06 at **87.6 % · 239 tests · 14 errors · 0 FAILED** (263 tests once the L2 suite landed).
Two reconciliations that cost time once and should not cost it again: the 14 errors are the sum of the
`corpus run` per-file `errors=` column, *not* what `biomd validate` reports (a different profile, 1 error);
and **PROGRESS §1's per-document table does not reproduce** — the aggregate is trustworthy, the breakdown is
stale, so re-measure before citing any per-document number from it.

**L2 — Structural adjudication. The primary instrument. Built 2026-08-06.** `src/eval/blocks.ts`
(`.bio.md` → typed, line-numbered block tree), `src/eval/structdiff.ts` (alignment + typed findings),
`src/eval/triage.ts` (three-way source backing), `src/eval/rollup.ts` (ledger + ranking), contracts in
`src/eval/structdiff.test.ts`, surfaced as `biomd diff [produced] [reference]` with
`--doc` / `--class` / `--backing` / `-v` / `--json`. Diagnostic-only: `convert-core` must never import it.
Two properties it is held to, and one law it earned:
*identity* — the same document on both sides yields zero findings, asserted over all thirteen references;
*determinism* — same inputs, byte-identical findings;
and **`evidence: "content" | "structure"`** on every finding, because §16.3 forbids inventing *text* and says
nothing about layout. The first build triaged structural findings by text attestation and buried
`columns.missing` — the largest reachable class in the corpus — in the ceiling list. Never route a wrapper,
a separator, a containment change or a geometric property through an attestation test.

The design it implements: parse both sides with
`biomd-ast/read()` — it already yields directive `name`, `props`, `propOrder`, `children`, line numbers and
warnings — align block sequences (ordered tree alignment, or LCS with recursive descent into directive
children), emit a **typed edit script**: `insert | delete | move | substitute`, each with both-side line
numbers, a node path and a defect class. Compare at full resolution, explicitly including everything L1
folds away: directive name *and every property value*; heading level, order and nesting; table cell
**coordinates** and column alignment; link label ↔ target pairing; image `alt` ↔ `caption` ↔ `size` ↔
`align` ↔ `link` binding; list type and nesting depth; `---` separators; blank-line and hard-break
structure; emphasis spans and nesting; inline typography (« », dashes, ellipses); entity decoding;
hyphenation artifacts; leading and trailing whitespace.
Output is *N localized findings*, never an average. A finding that cannot be acted on directly has a class
that is not yet precise enough — refine the class, not the tolerance.

**L3 — Rendered and geometric adjudication.** No bio.md → HTML renderer exists in this repo; build one as a
diagnostic (`tools/render-biomd.ts`), derived from `Biography-Markup.md` and modelling the target renderer's
known quirks — `biomd-ast/read.ts` documents several (the `PROPERTY_HEADER_DIRECTIVES` asymmetry,
`columns.divider` promoted to a synthetic first column) and `conformance.test.ts` asserts them. It is
diagnostic-only; the converter must never import it. **Invariant: both bio.md sides render through
identical code**, so any observed difference is attributable to the documents, not the tool — give it the
same file twice and the output must be byte-identical.
Then compare three ways in the built-in browser: source `.htm` render ↔ produced `.bio.md` render ↔
reference `.bio.md` render, served over HTTP so relative assets resolve (`.claude/launch.json`).
`read_page` for structure; `javascript_tool` for `getBoundingClientRect` / `getComputedStyle` on the exact
nodes in question; `computer` (`screenshot`, `zoom`) to see it; `resize_window` (desktop and mobile) to prove
a lane or pairing is real and not viewport-dependent; `read_console_messages` for parse fallout. Compare
reading order, block geometry, computed alignment, figure ↔ caption binding, column pairing and vertical
synchronization, table geometry, and whether the produced layout is *visually equal to or better than* the
source — the actual project goal, and the one thing no textual metric can answer.

Two verified facts about this corpus that shape L3 work:

- **Presentational attributes lie.** On `pavlov_azancheev.htm`, `align="center"` appears on `p.t8` (17×),
  `p.t` (16×), `p.t1`, `p.st` and `p.lt` — every one of which computes to `justify`. Only `p.t3` (3×) is
  actually centred. Computed style is the evidence; the attribute is not.
- **Computed `text-align` is not always the keyword you expect.** Chromium returns `-webkit-center` /
  `-webkit-left` for elements centred by an ancestor's `align` attribute — observed on `p` and `div` nodes
  without a class and on `div.advsp` in the same file. An exact `=== "center"` comparison therefore
  under-detects. `prominence.ts:132` and `structure.ts:1809` handle this; **`prominence.ts:138` and
  `structure.ts:1437` do not**, which is a live inconsistency, not a style preference.
- **No asset tree exists in this project.** `fixtures/html/` and `my-migration/html/` contain `.htm` files
  only; every referenced image, PDF and MP3 404s. Rendered pages will show broken images by construction —
  never chase that as a conversion defect, and remember that image geometry therefore rests on attributes
  and measurement fallbacks rather than on intrinsic dimensions.

**L4 — LLM adjudication.** A *judge* pipeline over the existing `src/llm` transport, strictly separate from
the production hooks:
- **side-blind** — randomize which document is A and which is B, run each pair in both orders, keep only
  findings stable under the swap; this removes position bias and most confabulation in one step;
- **localized and schema-validated** (zod) — every finding carries quoted spans from both sides, a node
  path, a severity, a defect class, and its source-backing verdict. A judge returning prose or a score is
  misconfigured; it returns findings;
- **strong model** (`claude-opus-5` via the `deep` slot), not the cheap `fast` model the production hooks
  use; a judge should not be the same model role whose output it judges;
- **calibrated before trusted** — run it against pages whose defects `analyze/analyze.md` already names.
  A judge that misses known defects, or reports defects no one can localize, is not usable yet; tune the
  rubric until it agrees with the human record, and report that agreement rate;
- **advisory only** — findings enter as *hypotheses* to confirm with L2/L3, never as ground truth and never
  as a target (invariant 3). Its unique value is what rules cannot see: whether a layout choice reads as the
  human migrator's intent, and which of two defensible renderings is better.
Cached and budgeted through the existing machinery; never required for a conversion to succeed.

**L5 — Human record cross-check.** Every complaint in `analyze/analyze.md` and every red/green region in
`design.png` maps to a defect class that is closed, open with an owning cell, or classified unreachable.
When instruments and the human record disagree, **the human record wins and the instrument gets fixed** —
a blind spot found this way is worth more than the defect that revealed it.

### 4.3 Defect ledger — the measure of progress

`analyze/defects.json`, regenerated by L2 and appended to by L3/L4/L5: stable id, class, severity, node
path, documents affected, instance count, source-backing verdict, status, owning rule and test, and the
mutation that would catch its regression. Progress is reported as **classes closed and instances remaining
per class**, with L1 alongside as a tripwire — never as an average. Rank work by
`instances × severity × generality`, where generality = how many documents and archetypes share the class.
Generality is the tiebreaker: a class recurring in six documents teaches more than a bigger one in a single
document.

### 4.4 Triage — mandatory, three-way, before any finding becomes work

Classify every L2/L3/L4 finding against the **source**:

- `source-backed` → a real defect; gets a work cell.
- `source-unbacked` → reference editorializing (invented headings, copyedited prose, `segovia`'s deleted MP3
  track table); recorded as a ceiling and excluded from targets.
- `ambiguous` → hook territory (§7).

Without this triage a deep diff floods the work with unfixable noise; with it, invariant 4 enforces itself.

### 4.5 Cadence

L0 + L1 every change · L2 every iteration and corpus-wide before every commit · L3 for every document
touched, all 13 at milestones · L4 batched per iteration, cost-capped · L5 at milestones.

### 4.6 Folds

**Never tune on all thirteen.** With 13 pairs, overfitting is the default outcome and no instrument
announces it. Hold out 3–4 documents unread while designing a rule; measure them only after the rule and its
tests are written. Rotate the holdout, report both sides. A rule whose holdout behaviour is far weaker than
its development behaviour is a special case in a general rule's clothing — generalize it or drop it.

Generalization beyond the 13 has no reference, so it has a checklist: crashes, validation errors, `read()`
warnings, conservation reports and `review()` escalations must not rise on any input outside the reference
set, including mutation fixtures.

## 5. Instrumentation

- **What the front half saw** — `biomd inspect <file>`; per-job artifacts in
  `my-migration/.biomd-work/<name>-<hash>/` (`00-source`, `07-output`, `08-validation/report.json`,
  `manifest.json`). The `Ledger`'s `review()` entries are the queue of decisions the rules gave up on.
- **Corpus-level evidence** — `biomd corpus scan` (template fingerprints, chrome model, lexicon). Detectors
  that generalize should be discoverable *there*, not per document.
- **HTML structure** — parse5/LADOM queried from a throwaway `node --experimental-strip-types` script, never
  by regexing `.htm`.
- **Text diffing** — `git diff --no-index --word-diff fixtures/out/X.bio.md my-migration/out/X.bio.md`,
  as a quick look only; L2 is the adjudicator.
- **External knowledge** — `WebSearch` / `WebFetch` for FrontPage-era markup quirks, CSS cascade edge cases,
  library behaviour. Cheaper than a wrong hypothesis.
- Scratch scripts, probes and notes belong in the session scratchpad directory, never in the repo.

## 6. Rule design for generalization

Every rule added or changed carries a **rule contract**, stated in the test file beside it:

- **Invariant** — the evidence it keys on, expressed without naming a document, class, id or literal:
  geometry (boxes, borders, widths, computed alignment), recurrence, containment, ordering, cardinality,
  typographic role. Prefer *relational* evidence ("centred on a page whose prose is not") over absolute
  thresholds ("width < 400 px").
- **Recurrence requirement** — the same shape must repeat on the page with content between occurrences.
  Every detector that survived here required recurrence; every single-block typographic threshold regressed
  it (PROGRESS §5, method note). This is a design law, not a heuristic.
- **False friend** — the near-identical shape it must *not* fire on. Each family has one: a caption
  resembles a heading, a menu label a section label, a record label a section, a copyright line a signature.
  Name it and test non-firing.
- **Mutation robustness** — the operational definition of "works on files never seen". A mutation harness
  derives variants from existing fixtures and asserts the produced **shape** (directive sequence with
  properties, heading levels, table geometry) is unchanged under: renamed classes and ids; permuted
  attribute order; added and removed wrapper nesting; dropped or duplicated closing tags; `<font>`/`<b>`
  swapped for equivalent CSS; Latin labels swapped for Cyrillic and back; different viewport widths;
  different encodings. Assert with L2, not with the scalar score.
- **Shape catalog** — a documented catalog of page archetypes (masthead + prose, prose with bound figures,
  discography grid, multi-column media/score table, dated news list, link farm, mixed single→multi→single
  column flow) with entry and exit evidence for each, and which defect classes each archetype exhibits. New
  pages map onto a known shape or announce themselves as unmapped. This is the assessment's page-archetype
  model, earned bottom-up from recurrence detectors instead of assumed top-down, and it is what makes the
  system extrapolate rather than accumulate patches.
- **Many small passes over one universal rule** (`analyze.md` item 9). Small passes compose, are
  individually testable, and fail locally. New passes run through `runPass`/`Ledger` so provenance and
  conservation stay auditable.

**Corpus facts a rule may assume**, because geometry confirms them corpus-wide: content is the centre column
(~½ viewport); page chrome and footer drop; right-hand menus fold into the main flow; most images are
captioned and centred or right-aligned; discographies and score/media lists run 2–5 columns; more than 5
columns, or a page dense with blockquotes, is an anomaly rather than a layout; vertically aligned blocks in a
multi-column region are semantically paired, and splitting such a region into several small tables to
preserve that pairing is legitimate. Original layout is preferred; where geometry cannot be proven, a cleaner
Markdown-native layout of equal quality beats a guessed one.

Content is Russian. Do not "correct" it beyond what the references demonstrably do.

## 7. Rules vs hooks

Rules handle what the source states. Hooks handle only what the source does not state.

Every production hook stays zod-schema-validated, budgeted, cached, replayable and **non-authoritative**: a
hook proposes, a deterministic check accepts or rejects, and the rejection path is tested. Add one only when
both the evidence rules cannot supply *and* the acceptance check that guards it can be named. A hook is also
the right home for judgement that will not generalize into a rule — but it must degrade to sane deterministic
output when disabled, since 1000 pages will not all be escalated.

Keep the production hook path and the L4 judge path strictly separate: different models, different prompts,
different purposes. Adjudicate with LLM off for comparability; measure the LLM-on delta as a separate,
explicitly labelled run.

Existing hooks: `table.classify`, `table.records`, `text.segment` (`src/llm/hooks.ts`).

## 8. Reporting conventions

Report defect classes and instances, not averages. State failures with their output. When something is
blocked, finish everything else and say precisely what is blocked and why.

At milestones, update `CONVERTER-PROGRESS.md` in the style it is already written in — measured numbers, what
was implemented, what remains reachable, what is provably unreachable — plus the shape catalog, the
instrument calibration record and the killed-hypothesis list. Those three are the parts a successor cannot
reconstruct.
